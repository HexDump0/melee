## P-765 — what was measured

The crash reproduces exactly as the brief says:

```
SIGSEGV in HSD_DObjSetFlags (dobj=0x40, flags=1)   dobj.c:33
  <- ftParts_80074D7C   ftparts.c:665
  <- ftParts_800750C8
  <- ftDrawCommon_80081200
  <- lbShadow_8000F38C
```

gdb probe (breakpoint `ftparts.c:663`, the `k < r26->x0` loop, logging every
TempS entry): 1025 hits, then

```
BAD temps 0x80adcafc x0=184549376 x4=0x80adcaf0
```

i.e. the crashing entry's `TempS.x0` reads `0x0B000000` — big-endian 11 —
and its `x4` points at a u8 DObj-index array whose first bytes are
`01 04 05 06 07 08 0a 0b 0c 0d 0e`: **exactly 11 consecutive indices**,
matching the count that was never converted. The full region around it
(`x/48xw r26-0x100`, saved mentally here) is a long TempS region full of
correctly-converted small counts (`{1, ptr}`, `{2, ptr}`, ...), so only this
one entry (plus possibly more after it — the loop died on the first) is cold.

### Neither of the two suspect guards fires on PlGw.dat

I instrumented `conv_ft_vis_lookup` temporarily (since reverted) and replayed
its walk on the raw file with a Python probe (`/tmp/opencode/probe_vis3.py`,
archive extracted to `/tmp/opencode/PlGw.dat`, FST offset `0x54658000`,
size `0x3f8e0`). For `PlGw.dat` (`model_num` = 11 confirmed at data offset 0):

- The `vis_table` (data offset `0x7c08`, 8x4 slots) has **real lookup pointers
  only in costume row 0**: `0x76e0, 0x7878, 0x7b58, 0x7bb0`. Rows 1-4 are
  all zero (so `ftParts_8007487C`'s `? : vis_table[0][col]` fallback always
  lands on row 0 — fine).
- All four lookup arrays walk their 11 model entries; per-model counts are
  small (max 8). **Guard (1) never trips** — no count is anywhere near 64.
- The `mark` `break`s that do fire (off=0x7bb0 m=1/6/7/8/10, i=0) all hit
  TempS entries that the *earlier* lookups already converted with the same
  or larger counts, so `break` vs `continue` changes nothing for PlGw.dat.
- After the walk, **zero** TempS entries in those four arrays read
  big-endian. The count that crashes is **not in the arrays the converter
  reaches through `vis_table`**.

### The lead this leaves

1. **Which fighter's archive is it?** The brief's repro says
   `MELEE_MATCH_P0=2 MELEE_MATCH_P1=3`, which is Ft_Kind_Captain /
   Ft_Kind_Donkey per `decomp/src/melee/ft/forward.h` (Fox=1, Kirby=4,
   G&W=0x18) — i.e. this exact repro is **not necessarily G&W**, despite the
   matrix title. I chased `PlGw.dat` on the brief's instruction and it is
   clean; the next step is to pattern-match the crash region against the
   *other* fighter archives:

   - run the repro under gdb with the `/tmp/opencode/gw-trace5.gdb` script
     (breakpoint `ftparts.c:663`, conditional `r26->x0 > 64`),
   - `dump binary memory` the region around the bad TempS (I dumped
     `0x80adc800-0x80adcc00` once; the bad entry is at `0x80adcafc`),
   - find which `Pl*.dat` raw bytes contain that pattern, and compute the
     data offset (archive base in the runtime is a flat buffer; the dump
     minus the buffer base gives the data offset),
   - then check whether that offset is inside a structure `conv_ft_vis_lookup`
     never reaches (per P-758, several `Pl*` files are 12-13% walked — an
     unwalked lookup array is likely).

   The sequence `01 04 05 06 07 08 0a 0b 0c 0d 0e` (11 consecutive u8
   indices immediately followed by the word `00 00 00 0b`) is a strong
   needle for a `grep`-style search across the raw archives.

2. **A separate converter bug found on the way (worth its own task).** In one
   of the `PlXxNr.dat` conversions the trace shows `conv_ft_vis_lookup`
   walking `off=0x18` — the **public-symbol string region**
   (`"PlyGamewatch5K_SHARE_ACTION_DamageFall_fightree"` lives at data
   `0x18..0x44` in PlGw.dat; the same shape is in the Nr files). That walk
   `conv_u32`'d ASCII words, i.e. byte-swapped symbol-name bytes. Root shape:
   a `vis_table` slot whose word is a relocation target but whose *value* is
   not a lookup array (the slot words for costume rows 1-4 are zero, but at
   least one slot in an Nr file relocates to data offset `0x18`). The
   costume-loop guard `if (!c->reloc[p]) ended = 1;` trusts `reloc` alone;
   the value `0x18` passes. A "pointee looks like `{small count, data
   pointer}` x model_num" check (the `looks_like_unconverted_joint`
   precedent from P-748/G-183) would have rejected it. Note the crash value
   `0x0B000000` also appears in that runaway region's garbage, which is
   suspicious — verify whether the two are connected before assuming.

### Things ruled out for P-765 (so nobody re-does them)

- Not P-764's bug: the `ended`-flag fix is in (v101) and this crash survives.
- Not guard (1) `count > 64` on the reachable arrays: all counts <= 8.
- Not `mark`-false abandoning a shared TempS array: every observed `break`
  was at i=0 on an already-fully-converted region.
- `dobj_list` (count 116) and the u8 index bytes themselves are fine; the
  crash is purely the cold `TempS.x0`.
