# Handoff — 2026-09-18, P-847 (the Master Hand fight's camera)

Read `native/AI/AGENTS.md`, then G-205 and the P-847 row.
Third crash of the day from the same Classic playthrough, after P-845 (Race to
the Finish) and P-846 (the team-battle splash).

## What the report gave away

```
#4 lbVector_WorldToScreen  #5 Camera_80030BBC  #6 Camera_80030CFC
#7 ftLib_80086A8C          #8 ftDrawCommon_80080E18
```

`ftLib_80086A8C` runs while *drawing a fighter* and asks whether its camera box
is on screen. The position it projects is built from the camera's eye and
interest, so a `pos3d` outside ±50000 means the **camera** is bad, not the
fighter — and the dump agrees: both bone chains are sane, and
`cambox pos=(50,52,0)` is `cur_pos + (0,22,0)`, which is Master Hand's
`ftData->x3C[0] = 22` read correctly. (That check is worth keeping: it rules
out the whole converter family in one line.)

The dump's `mv.pk.speciallw.x0=0x1` is the same union member as
`fp->mv.mh.unk4.x0`, so the entry cinematic had just run its `Unk00` arm.

## The defect

`ftmasterhandentry.c:70` sets up the boss camera with `Camera_8002ED9C(40)`
(distance), `Camera_8002EC7C(-PI)` (yaw) and `Camera_8002EF14()`. That leaves
`x35C.bits.b0` and `b2` set and **`b1`, the pitch, clear**.

`Camera_8002E234`'s `case 2` writes `sp10`, `spC` and `sp8` only inside the
three matching `bits.b*` guards, then reads all three unconditionally:

```c
lbVector_Rotate(&sp14, 1, -sp10);   /* pitch  -- never written */
lbVector_Rotate(&sp14, 2, spC);
temp_f31 = sp8;
...
game_camera.transform.position = sp14;
```

So the camera's eye position came from a stack leftover. G-205's family, for
the fourth time.

**The fix is not "do nothing".** `Camera_8002F0E4` fills `x368` from the live
camera as the *start* of the interpolation those three calls run, so holding
`x368` is exactly what "this axis is not animated" means — and it is what the
console gets by accident, since the slot at that depth holds the previous
frame's value of the same local. `#ifdef PORT_PC`, mirrored to
`patches/src/melee/cm/camera.c.patch`, listed in `learnings/decomp_port.md`.
GameCube build re-verified: **100.00% matched, 100.00% linked (1130/1130)**.

## How it was measured, and the knob that made it possible

The Classic Master Hand fight is the **eleventh round**; no harness can win ten
matches to reach it, and jumping the Classic state machine there does not work
(the character-select scene's exit callback rewrites both the chosen character
and the next state id — I tried, and reverted it).

`MELEE_BOSSCAM=<frame>` instead runs the entry camera sequence on an ordinary
VS match:

```sh
MELEE_BOSSCAM=800 MELEE_MATCH_P0=0 MELEE_MATCH_P1=1 MELEE_MATCH_STAGE=32 \
  MELEE_NO_CARD=1 SDL_VIDEODRIVER=offscreen SDL_AUDIODRIVER=dummy \
  ./build/native/melee --match 600 --frames 1100 --no-items
```

Without the fix it panics on that exact frame, and the backtrace is
**identical to the owner's, frame for frame**. With it, 1,100 frames clean.
ctest 34/34.

**This should be a ctest.** It is one command and it guards a screen nothing
else reaches. It is not wired in yet only because `native/CMakeLists.txt` had
another session's uncommitted work in it at the time; add it there when the
file is free.

## Still open from the same report

**`GrNBa.dat` (Battlefield) renders as giant shards** — the owner's viewer
screenshot, and it is not a viewer artifact: a normal headless match on
`MELEE_MATCH_STAGE=31` looks the same. Worth knowing before someone starts:
`test_decomp_render --stage GrNBa.dat --no-fighter --dump` puts the first nine
draws at view-space bounds up to ±3424 with z from -7192 to **-246**, while the
stage proper sits at ±80 around z -600. So the *background* object is both far
too large and reaching in front of the stage. Other stages (GrYt, GrNLa,
GrNPo) render correctly, so it is specific to this archive.
