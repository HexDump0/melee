  Runs `melee_decomp_boot` over N seeds in parallel, classifies each run by
  grepping the log, dedupes failures by assertion text, and prints
  `failure -> count -> example seeds` with a repro command and a backtrace per
  distinct failure.
- **P-762, Great Bay.** `conv_itemdata` swapped each `GroundItemData`'s item
  kind and never followed the `Article*` beside it, so an entire model tree

- **P-757, the DWARF cross-check.** `native/tools/` + ctest `decomp_layout`.

## Exact next action

**P-758 is unblocked — all four gates are in place.** Start with `Vi*`, which
is 11 files at **0.9%** (1,096 descriptors) and almost certainly one missing
root rule, so it is the cheapest item on the board. Then the `Pl*` shared
cause: several fighters sit under 20% while `ItCo` is at 86%, which says
per-character `ftData` sub-structures are reached for some kinds and not
others, not 241 independent problems.

The method that worked on P-762, in order:

```sh
# 1. reproduce and get a stack
MELEE_NO_CARD=1 MELEE_RNG_SEED=<seed> ./build/native/melee_decomp_boot \
    --boot-frames 900 --boot-timeout 90 --boot-match 20
# 2. trace the broken descriptor back to whoever should have reached it
MELEE_NO_ASSET_CACHE=1 MELEE_FIND_PTR=0x<offset> ... 2>&1 | grep findptr
# 3. name the nearest public root at or below it
MELEE_NO_ASSET_CACHE=1 MELEE_ROOT_TRACE=1 ... 2>&1 | grep 'convert. root'
```

The fix goes where the **reference chain** is broken, not where the crash is:
P-762's crash was in `pobj.c` and the bug was in `conv_itemdata`, four levels
up. `conv_pobj` was correct all along — that PObj was simply never reached.

**What each new walker owes the three ratchets**, all of which fail the build
rather than the player:

1. `/* DWARF: <Type> */` above it, and raise the `decomp_layout` floor
   (currently **49**) in `native/CMakeLists.txt`. If the type has no DWARF,
   add its header to `native/tools/dwarf_types.c` — an annotation naming a
   type the tool cannot find is a **failure**, not a pass.
   `python3 native/tools/check_walker_offsets.py build/native/dwarf-layout.json \
   native/decomp/assets/hsd_convert.c --list-unannotated` prints the worklist.
2. Raise `MELEE_COVERAGE_FLOOR` in `native/tests/test_decomp_assets.c` by what
   the walker actually gained. Measure it with
   `MELEE_NO_ASSET_CACHE=1 ./build/native/test_decomp_assets "iso/<image>.ciso"`
   and read the **second** coverage line.
3. Leave `decomp_soak` green, and **bump `HSD_CONVERTER_VERSION`** — the cache
   in `~/.cache/melee/assets` is keyed by it, and editing a walk without
   bumping it means stale entries answer instead of your code (G-177/G-178).

## What I tried that did not work

- **Annotating walkers by inserting above the first regex match of the
  function name.** The forward-declaration block at the top of `hsd_convert.c`
  has the same shape as a definition, so 27 annotations landed on
  declarations. The parser had the mirror image of the same bug: it opened a
  walker on a forward declaration, then swallowed the next real function's
  body, and silently mis-attributed two walkers while still reporting PASS. If
  you extend the tool, **match the definition by requiring the line not to end
  in `;`** — and check the walker count, not just the exit status.
- **Believing a green cross-check.** The first clean run was clean because the
  parse was wrong, not because the offsets were right. Every check in this
  commit was afterwards verified by *injection* — a wrong offset, a swapped
  pointer field, a wrong access width, a wrong size macro, a removed
  annotation — and P-762's regression test by reverting the walker. A gate
  nobody has watched fail is not yet a gate.
- **Two size "mismatches" that were not bugs.** `conv_cobjdesc` bounds itself
  at 0x30 against a 0x40 union, and `conv_ps_cmd_list` at 0x3C against 0x40.
  Both are deliberate and documented in place (union variants; a trailing byte
  stream that must stay raw). Rather than delete the size check I added
  `DWARF: <Type> partial`, so a short bound is a decision on the record
  instead of a silent one. **Do not "fix" either walker to cover the full
  size** — swapping `cmdList[]` would trade a crash for silently wrong
  particle behaviour, exactly like the fighter subaction scripts in G-178.
- **`ALDYakuAll` as P-762's missing root.** The previous session had already
  ruled it out and its row said so; it is the nearest non-image root below the
  chain, but `ground.c:493` assigns its entries to `itemStateDesc[].xC_script`
  and those are item-state byte streams. The real referrers turned out to be
  `ItemModelDesc.x0_joint` fields belonging to the stage's Article, which
  `itemdata` names from a completely different offset. **The nearest root
  below a broken descriptor is a hint, not the answer.**

## Open questions

- **Bit-field bit numbering is still only covered by `check_unk_flag_bit_order`
  and the 6 `PORT_BF_BE` sites.** `decomp_layout` counts bit-field accesses
  separately (currently 0) so the hole stays visible, but it will never close
  it — the native DWARF is GCC's LSB-first allocation. Building the matched
  DOL with `-g` is the only way to check the disc's own bit order from debug
  info, and ADR-0024 declines to risk the `100.00%` match for it. Revisit only
  if a bit-order bug actually escapes. Needs a human? **no**.
- **226 accesses go through a computed base** (`e = off + i * 0x10`, the array
  walks) and cannot be checked as a flat struct. Covering them means teaching
  the tool about strides, or restructuring those walkers to convert one element
  through a named helper. Worth doing only if a stride bug shows up. Needs a
  human? **no**.
- **`ftCo_AttackEntry` is defined in `ftcpuattack.c`, not a header**, so
  `FT_CPU_ATTACK_ENTRY_SIZE` (0x24) has no DWARF to check against. Same for
  any other `.c`-local type. Needs a human? **no**.
- The soak runs one scenario (`--boot-match 20`, the built-in script) across
  seeds. **Fighters x stages is not covered yet** — that is the "matrix" half
  of P-759's original title, and it needs `melee_decomp_boot` to take a
  character/stage selection. Worth doing before the nightly full-matrix soak in
  ADR-0023 phase 4. Needs a human? **no**.
