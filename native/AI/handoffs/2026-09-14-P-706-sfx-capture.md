## What I did

- Added `native/audio/sfx_debug.{c,h}`, an opt-in recorder selected with
  `MELEE_SFX_DEBUG=<path>` (`1` = `melee-sfx-debug.log`, `-` = stderr).  It
  observes four boundaries and never changes playback:
  - accepted driver requests (`AXDriver_8038CFF4`, with the original and
    internal sound IDs, volume/pan/track/channel),
  - actual synth voice starts (`HSD_Synth_80389334` by way of
    `AXDriver_8038BF6C`),
  - sample-loop wraps and per-voice totals in the host mixer
    (`ax_mixer.c:voice_decode_frame`),
  - the final mixed PCM (`ax_hle.c:__AXOutNewFrame`, peak/clip/active-voice
    accounting).
- Fighter attribution: a `PORT_PC` hook in `ft_PlaySFX` (`ft_0877.c`) records
  `player_id/kind/motion_id/cur_pos` around the nested request, so a request
  line names the fighter and state that asked for the sound.  A second hook in
  `HSD_SynthSFXPlayWithGroup` maps the second voice of two-voice SFX.
- Output shape:
  - `[sfx-window]` once per second: request/start/failure/loop counts, active
    voices, peak and clipped-sample counts, and the top three IDs.
  - `[sfx-alert]` on: 4 requests for one ID within 2 s, 3 wraps of one mapped
    voice within 3 s, 20 consecutive frames with clipped samples, or 20
    consecutive frames with ≥48 active voices.  Each alert dumps scene/mode,
    every live fighter, the rolling 64-request history with fighter context,
    every active voice with AX address/loop/end/ratio/VE/mix state and its
    mapped sound ID, plus a symbolized call stack.
  - `[sfx-summary]` at exit (`atexit`, so ESC-quit still writes it): totals,
    top 12 IDs, current game state, recent requests and active voices.
- Verified the disabled path is behavior-neutral: `decomp_audio` still proves
  two scripted matches render byte-identical PCM.
- Wired only the product target and the shared AX sources; the boot/test
  targets compile the recorder as a no-op (env unset in every ctest).

## Exact next action

Wait for the owner's capture, then read it in this order:

1. `grep '\[sfx-alert\]' <log>` — the loud incident should have one or more
   alerts near the reported time.  `reason=` classifies it:
   - `same-id-requests` + a small set of IDs → the game is re-requesting an SFX
     (look at the fighter/motion lines and the call stack; compare against the
     IDs in `ftData->x4C_sfx` and `ftColl_803C0C40`).
   - `short-voice-loop` → one voice is wrapping a bad/too-short sample; the
     `[sfx-loop]` line's `from/loop/end/ratio` gives the address span.  Check
     whether `end - loop` is plausibly the sample length.
   - `sustained-clipping` / `voice-saturation` → the mix itself is overdriven;
     check whether many voices stack or one voice's VE ramp pins high.
2. `grep '\[sfx-window\]' <log>` around the incident for the rate ramp.
3. The `[sfx-summary]` tail for peak/clipped maxima.

If the incident does not reproduce with the recorder running, ask for a second
capture; the recorder is passive, so it cannot mask the bug.

## What I tried that did not work

- Mapping voices purely from `HSD_Synth_80389334`'s return (node id): the
  node's `x0` is `(vidhigh << 7) | slot`, not the AX voice index, so the first
  version left almost every voice `id=-1`.  Fixed by tracking the node handle
  from `AXDriver_8038CFF4` and resolving primary/secondary voice indices from
  the node after `HSD_Synth_80389334` returns (a `PORT_PC` hook in
  `HSD_SynthSFXPlayWithGroup`).
- Clearing a just-started voice on the first post-start mixer frame: the mixer
  still sees the old idle shadow once before the voice flips to state 1; the
  recorder now retains a mapping created in the current audio frame.
- The first hunk-header arithmetic in the hand-edited `synth.c.patch` was
  wrong twice (`@@ -678,6 ...` vs the real 5-line window); `git apply --check`
  catches it immediately — always run `scripts/apply_decomp_patches.sh` (or
  `git -C decomp apply --check`) after editing a patch by hand.
