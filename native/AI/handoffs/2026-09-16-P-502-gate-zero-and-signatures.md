## The GameCube build now actually runs, and it earned its keep

Nobody had run it: `decomp/orig/GALE01/sys/` was empty, so `ninja` could not
split the DOL, and every previous claim of "GC still matched" rested on a
preprocessor token-stream argument. It is a five-minute setup:

```sh
cd decomp
python3 configure.py
# tools/download_tool.py fetches dtk, wibo, sjiswrap, binutils and the MWCC
# bundle (~90 MB total).  It hung once on GitHub; curl the URLs it prints
# into build/tools/ by hand and re-run if that happens.
build/tools/dtk disc extract "../iso/<your image>.ciso" /tmp/disc
cp /tmp/disc/sys/main.dol orig/GALE01/sys/main.dol   # gitignored, never commit
ninja                    # ~20 min, 1144 targets
build/tools/dtk shasum -c config/GALE01/build.sha1
```

**It caught a regression the token-stream argument could not.** The first build
came out at 99.97% with exactly one function short: `it_802790C0` at 99.71%.
The cause was this, in `itanimlist.c`:

```c
union CmdUnion* u = cmd->u;
u32 hitbox_idx = u->it_create_hitbox_0.id;   /* became CMD_U(cmd)->... */
```

`CMD_U(c)` expands to `((c)->u)` on the GameCube, so the *tokens* are
equivalent -- but the original reuses a pointer MWCC has already loaded, and
the rewrite makes it load `cmd->u` again. Same meaning, different instructions,
no longer a match. Gated under `PORT_PC`; **`main.dol` is now
`08e0bf20134dfcb260699671004527b2d6bb1a45`, byte for byte the retail binary,
1130/1130 files, 19,828/19,828 functions.**

The lesson generalises: a macro that expands to "the same expression" is not
free on a matched build. Anything that touches an expression MWCC compiles
needs the real build, not an argument about tokens.

## Corrections to the previous handoff

Three of its statements are wrong, and two of them would cost the next agent a
day.

1. **`-sEMULATE_FUNCTION_POINTER_CASTS=1` was never in the build.**
   `wasm_census.sh` has never carried it; the tree has no reference to it
   outside that handoff. The build linked and ran without it, so there was
   never 2 MB or any speed to recover -- only the three declarations to fix.
2. **"Byte-swap the subaction stream at load" is not available.** The
   handoff's argument is that `sizeof(CmdUnion) == 4` and `NEXT_CMD` is
   `++cmd->u`, so a script "is a uniform array of 32-bit words". It is not.
   `Command_05` (Subroutine) and `Command_07` (Goto) carry a **relocated host
   pointer** in the word after the opcode (`lbcommand.c:61,74`), so a blanket
   swap corrupts every jump in the game. Finding the scripts is the other half
   of the problem and is G-178 exactly. This route is closed; see G-190.
3. **Gate zero was wider than "the `CMD_BE` structs".** `PORT_BF_BE` in
   `Runtime/platform.h` is a second `scalar_storage_order` macro, and there
   were four more sites past the 76: `gmScriptEventDefault` and three unnamed
   groups in `union ColorOverlay_x8_t`. All are fixed.

## Gate zero: how it is fixed (P-796)

**State the layout, do not ask a compiler for it.**
`native/decomp/shim/decomp_cmd_bits.h` declares all 76 command structs over one
32-bit word in **host** order -- the console's fields reversed and padded to the
top of the word -- and `CMD_U(cmd)` byte-swaps that one word where it is read:

```c
#define CMD_U(c) (&(union CmdUnion){                                  \
    .host_word = __builtin_bswap32(*(u32 const*) (c)->u) })
```

so `cmd->u->spawn_gfx_0.boneId` became `CMD_U(cmd)->spawn_gfx_0.boneId`, 176
sites across `ftaction.c`, `itanimlist.c` and `lbcommand.c`. On the GameCube
`CMD_U(c)` is `((c)->u)` and the line means what it always meant. The same
shape, `CO_X8(p)`, serves `union ColorOverlay_x8_t`. `PORT_BF_BE`'s two groups
live in **one byte**, where there is no byte order to get wrong, so they are
simply padded and reversed in place. **No `scalar_storage_order` is left in the
tree.**

The header and the test's field table are generated by
`native/tools/gen_cmd_bits.py`; `--check` fails if either drifts from
`<melee/lb/types.h>`, and `wasm_census.sh` runs both the check and the test
under node after linking.

### The regression this caused, and the lesson

The first version of this change **crashed the scripted match at frame 532**
(`lb_80014258` -> a garbage function pointer). The cause was not the layout --
that was already proved correct -- it was that the sweep for read sites was a
grep for the **member names I already knew**, so it missed four reads of
`unk.unk` / `unk.timer` in `lb_013B.c`, two through a local alias
(`union CmdUnion* u = cmd->u;` in `itanimlist.c`), and, in a different shape
altogether, `itsamusgrapple.c`.

**Grep for the pointer, not for the members.** `x8_ptr1`, `->u`, and the struct
tags each find sites the others miss.

`itsamusgrapple.c` is worth reading before touching any of this again: it is
**compiled C data**, not archive bytes, so its representation only has to be
self-consistent -- but it was written *positionally*
(`{ 11, 0, 0, 0, 139, 0, 0 }`), and it read two fields through **byte aliases
that assume the console's byte order** (`*(u16*)(data + 2) & 0x3FF` is
`create_hitbox_0.damage`; `hitbox_flags->hit_grounded` is
`create_hitbox_4.hit_grounded`). Those are now designated initialisers and
named field reads under `PORT_PC`, which incidentally fixes two endian bugs
that predate this work.

### Why you can trust the desktop is unchanged

- A generated differential program compiled **both** declarations -- GCC's
  `scalar_storage_order` version, extracted verbatim, and the new one -- and
  compared every field of every struct over 4,000 words: **924,000 reads, zero
  differences.** The same was done separately for the `ColorOverlay` and
  `PORT_BF_BE` groups.
- `ctest bit_order` now walks all 231 fields against the console's arithmetic
  and passes identically under GCC and under Emscripten. A deliberate
  one-struct perturbation fails it, so it is not vacuous.
- `decomp_match` pins an exact trajectory and reproduces it.

## Signature mismatches (P-797)

All three were the same thing: a caller's local `extern` disagreeing with the
definition, which GCC accepts in silence and `wasm-ld` reports, and in each
case the **console was passing a value in `r3`** across a call the
decompilation writes as `void`.

| symbol | what the console does |
|---|---|
| `ftLib_800876B4` | falls out of `ftAnim_IsFramesRemaining`, so `gm_1798.c` -- which declares it `s32` and tests it -- reads that result |
| `gm_801677E8` | takes `mn_802295AC()`'s result; `mnhyaku.c` calls the two in sequence, and `mnevent.c:502` spells the same pair out as one call |
| `mnCharSel_802640A0` | returns `s32`; `mnmainrule.c` declares it `void` |

Fixed under `PORT_PC`. The link is clean. Expect more of the class only from
*casts at call sites*, which the linker cannot see -- the engine's callback
tables are the place to look, and wasm traps on a mismatched `call_indirect`
rather than misbehaving, so they will announce themselves.

## Open: the DevCom alignment crash (P-798) -- needs one browser run

`HSD_ASSERT(0x1F0, dest % 32 == 0)` at the title -> menu transition, browser
only. **Ruled out already:** `OSSetArenaLo/Hi` are `0x80003000`/`0x81800000` on
both targets, and every archive load goes `lbHeap_80015BD0` -> `HSD_MemAlloc`
-> `OSAllocFromHeap`, which is 32-aligned by construction (`OSAlloc.c`,
`ALIGNMENT 32`). So the unaligned destination is most likely an **ARAM** one
(`lbfile.c:126` picks the type by `dst >= 0x80000000`, so an ARAM destination
is a small offset, not a pointer) or one of `synth.c`'s sample-bank loads.

The diagnostic in `patches/src/sysdolphin/baselib/devcom.c.patch` now prints
the decoded dest type **and, under `PORT_WASM`, an
`emscripten_get_callstack()` backtrace**, so one run should name the caller.

```sh
source ~/projects/emsdk/emsdk_env.sh
native/tools/wasm_census.sh /tmp/w
cd /tmp/w && python3 -m http.server 8801 > srv.log 2>&1 &
# Then CHECK IT IS YOURS before asking the owner for anything:
curl -s -o /dev/null -w '%{size_download}\n' http://localhost:8801/melee.wasm
stat -c%s /tmp/w/melee.wasm          # the two numbers must agree
# open localhost:8801/melee.html, pick the .ciso, press Enter at the title
tr -d '\0' < srv.log | grep -oP 'GET /(L|ABORT)/\K[^ ]*' \
  | python3 -c "import sys,urllib.parse;[print(urllib.parse.unquote(l)) for l in sys.stdin]"
```

**Do not reuse port 8790, and do not trust an HTTP 200.** Previous sessions
left servers running on 8741, 8752 and 8790; `python3 -m http.server` dies
immediately with `Address already in use` and, if you backgrounded it, says so
only in its own log. `curl` then answers 200 from *somebody else's* directory
and the owner runs a stale build. It cost a round trip here: the owner's run
came back with `devcom.c` **line 410** and no `DevCom UNALIGNED:` line, which
is how we know it was a build with no diagnostic patch at all -- 410 is where
`dest % 32 == 0` sits in the *pristine* file, 421 with the patch applied. The
byte size of `melee.wasm` is the cheap way to tell builds apart.

**Delete the diagnostic patch with the fix.**
