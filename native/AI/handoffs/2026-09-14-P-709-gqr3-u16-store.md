## Where this comes from

Cross-port review of [`999sian/melee-pc`](https://github.com/999sian/melee-pc)
(a 64-bit + Aurora port pinned to the **same upstream commit** as us,
`40012f51f`).  Two of our decisions came out wrong or unfinished:

1. The P-687 `fn_80166A8C` fallback (`d2b3ab26c`) follows upstream
   `doldecomp/melee#3456`'s reading that the `psq_st` is a *float* store.
   It is not — it is a **GQR3 quantized u16 store**, and the caller reads a
   u16.  See G-158.
2. `ftAnim_8006F3DC` fell off the end on its not-found path; the P-695
   census left it alone as "never observed".  melee-pc fixed it to return
   `0.0f`.  See G-159.

## Fix A — `fn_80166A8C` must store a clamped u16

**Current port code** (`patches/src/melee/gm/gm_1601_ml_fallback.patch`):

```c
#elif defined(PORT_PC)
    /* psq_st with W=1 through GQR3 (float type, no scale) is a single-element
     * float store: x reaches dst->x and is also the return value.  The
     * caller reads sp48_x after the call. */
    float x = src->x;
    dst->x = x;
    return x;
#endif
```

**Why it is wrong.**  `init_spr_unk` (`decomp/src/melee/gm/gmmain.c:107-120`)
runs `MTSPR(0x393, 5)`, i.e. `li r3, 5` + `oris r3, r3, 5` -> `r3 =
0x00050005` -> SPR 0x393 = GQR3.  GQR store type 5 is **U16**, scale 0, so
`psq_st x, Vec3.x(dst), 1, qr3` writes a clamped 0..65535 halfword (and the
source float stays in `f1` as the return value).  GQR2/4/5 are set to
`0x00040004/0x00060006/0x00070007` in the same call — the U8/S8/S16 family,
which is the pattern confirmation.

The caller `gm_80166378` (`gm_1601.c:3005-3008`) does:

```c
cnt = Player_GetJoystickCountByIndex(i, 0);
sp48_y = (a = 0.031f) * ((f32) cnt * fn_8016B5B0());
fn_80166A8C((Vec3*) &sp48_y, (Vec3*) &sp48_x);
arg0->player_standings[i].xE = *(u16*) &sp48_x;
```

`xE` is the joystick-activity score; `fn_8016B5B0` (`gmvs.c:423`) is the
player-count coefficient (0.9/0.8/0.7 for 2/3/4 players, 3.0/3.3 in 1P), and
`gm_801688AC`/`gm_80168940` -> `gm_8016247C` (`gm_1601.c:1332`) accumulate it
into the persistent/session high-score fields with `0xFFFFFFFF` saturation.
With the float store the caller's u16 read returns mantissa bits.

**Correct fallback** (melee-pc reference, `src/melee/gm/gm_1601.c:3094-3106`):

```c
#elif defined(PORT_PC)
    /* init_spr_unk sets GQR3 = 0x00050005 (type 5 = U16, scale 0), so the
     * psq_st writes a clamped halfword and returns the float in f1. */
    float x = src->x;
    *(u16*) dst = (u16) (x < 0.0f ? 0.0f : (x > 65535.0f ? 65535.0f : x));
    return x;
#endif
```

Use whichever clamp spelling matches the file's style; the store width and
clamp are what matter.  Also correct the comment: it is not a float store.

**Note for upstream:** issue #3456's suggested `dst->x = x` fix is wrong on
this one point; it may be worth a comment to the author after we land ours.

## Fix B — `ftAnim_8006F3DC` return on the not-found path

`decomp/src/melee/ft/ftanim.c:552-573`; when `x8A4_animBlendFrames == 0` and
the loop finds no part with `flags_b1 && !b0 && !b5` (or a matching part has
`joint->aobj == 0`), control reaches the closing brace.  Callers
(`:371-376`) do `if (ftAnim_8006F3DC(gobj) < fp->cur_anim_frame) ...` and
`fp->cur_anim_frame = ftAnim_8006F3DC(gobj);`.

The P-695 census deliberately left it (retail returns the caller's `f1`,
"never observed").  melee-pc chose a defined value in commit `21da73a09`
("Fix functions that fell off the end returning garbage on x86-64"):
"`ftAnim_8006F3DC` returns a defined `0.0f` when no animated part matches."
Add `return 0.0f;` to the existing `patches/src/melee/ft/ftanim.c.patch`
(the patch already adds `ftAnim_8006F994`'s `return joint;`).
