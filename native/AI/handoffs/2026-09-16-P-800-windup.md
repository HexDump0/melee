## What was fixed

**P-796 — Brinstar's acid segfaults the first time it buries a fighter.**
`conv_yakumono_param`'s Zebes branch converted the bury descriptor five words
deep, so `element`, `sfx_severity` and `sfx_kind` stayed big-endian;
`sfx_kind = 8` arrived as `0x08000000` and indexed a 42-entry table 400
million entries out. **P-785 fixed this exact five-vs-nine split in
`conv_dynamics_desc` and this second copy of the walk was missed** — when you
fix a walker, grep for other copies of the same walk before closing the row.
Found only because the matrix was run at 5400 frames instead of 900; the
fifteen-second run never reaches the acid.

**P-798 — every float immediate in every particle command script was
byte-reversed.** `psReadFloat` assembles them a byte at a time into a
`union { f32; u8[4] }`, `bytes[0]` first; that byte is the most significant one
on PowerPC and the least significant one on x86. `psDispSub` scales the
billboard axes by `pp->size`, so one reversed size immediate is a sprite a
hundred billion times too large, rasterising as a flat wall of one texel —
the owner's screenshot of Bowser's fire breath covering half the screen, and
"the right part of the screen flashing white" on other characters' moves was
the same bug rather than a second one. The particle command bank is an opcode
stream, so nothing can byte-swap the floats inside it without decoding every
opcode; it has to be fixed at the read. **Same class as P-788 — that is now
three command streams with this bug, and any byte-wise or cast read of archive
command data is worth auditing as a class.**

**P-799 — GX point and line raster sizes are `u8` in 1/6 pixel units** and the
backend passed the raw byte to `gl_PointSize`/`glLineWidth`, so every point
sprite was six times too wide in GX pixels and wider again on a taller
framebuffer. Fountain of Dreams' sky drew ~10 px flat grey squares where 1–2 px
twinkles belong. See G-191 and G-192: `decomp_efb` encoded the same wrong
assumption and agreed with the bug, and the shape of the artifact argued
convincingly for a texture-coordinate cause that a one-line census disproved.

## What is open and what to do next

**P-797 — the owner's `lbvector.c:398` `pos3d->y` assert in Classic.** Not
reproduced. It is the `y` assert, not P-772/P-781's `x`, so **one component is
bad and the others are not**, which rules out a garbage matrix and points at a
single float. A healthy camera-bone chain has a **pure-Y** translate two levels
above the root (the joint `ftAnim_8006E054` rewrites as
`animated_translate - x68C_transNPos`), so a bad TransN Y or `HSD_A_J_TRAY`
track corrupts `y` alone — the P-781 family with `TRAY` for `TRAZ`. The scene
is `gm_Mode_Classic_States+180`, element 7's `info`, i.e. route entry 3 with
flags `0x00`: an ordinary 1v1, so the VS soak is the right tool. Any
reproduction now self-reports.

**P-800 — SIGSEGV in Pikachu's Thunder (`itpikachuthunder.c:112`).** Not
reproduced over four special directions, 5400 frames, three stages, two seeds,
items on. The fault is `ip->xC4_article_data->x4_specialAttributes` reached
from `fp->mv.pk.speciallw.x0`, which the caller null-checks but cannot check
for staleness.

**Read the correction in the P-800 row before theorising.** My first pass
claimed the dump showed "Peach and Fox and no Pikachu" and built a whole
gobj-teardown / Training-character-swap theory on it. `Fighter::kind` is a
**`FighterKind`**, not a `CharacterKind` — `Ft_Kind_Pikachu` is **12** — so
fighter #0 *was* the Pikachu, airborne at `y = -45.67` and falling. Both
instruments were right and my reading of one was not (G-190). The dump prints
the kind by name now.

What is established: the union puts `specialhi.x0/x4` and `speciallw.x0/x4` on
the same words; `Enter` clears `x0` and sets `x4 = 1`; the animation loops bail
when `x4 == 3` **before** calling `ftPk_SpecialLw_8012765C`, so the ordinary
"item destroyed" path is already guarded. The crash therefore needs `x4` still
1 while `x0` dangles, and `it_2725_Logic39_Destroyed` has three conditions that
can skip the notification — `ftPk_SpecialLw_CheckProperty` is one, and it is
true while the fighter is in a damage-ish state, which is exactly what happens
if Pikachu is hit mid-Thunder. Ruled out: a `bool` width mismatch on `x4` (the
decomp's `bool` is `int` in both builds) and a bad pointer from a failed spawn
(`it_802B1DF8` dereferences the same chain itself at spawn time, so it was
valid then).

Still open is why the console tolerates the dangling read and we do not. The
faulting address now on the stop line answers it directly: `0xc4` means `ip`
was NULL, `0x4` means `xC4_article_data` was, and a wild value means a stale
pointer into freed memory. The owner reproduces this trivially, so one run on
the rebuilt binary is worth more than more sweeping.

## Instruments added this session

- **`match_boot_dump_fighters`** runs from `__assert`, `HSD_Panic` and the
  signal handlers. Prints every live fighter's `cur_pos`/`prev_pos`/
  `pos_delta`/`self_vel` — `prev_pos` is last frame's value, so an
  *integrated* runaway is distinguishable from a *written* position without a
  second run — the camera bone's joint chain to the root with `<== BAD` on the
  first out-of-range level, the in-proc gobj, and every live item.
- **`controlled stop: SIGSEGV at <addr>`** — `si_addr`, which separates a NULL
  base with a struct offset added from a dangling pointer.

  filtered to direct-mode positions (`pobj.c` is the only
  `GXSetArray(GX_VA_POS)` caller, so indexed positions are models and direct
  ones are the effect path). Answers "geometry or shading" in one run.
