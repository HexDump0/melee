## Exact next action (the blocker)

The boot stops at:

```
in ftCollisionSetHitStatus illegal parts!
assertion "0" failed in src/melee/ft/ftcoll.c on line 3171
```

Root cause: **archive action command scripts are big-endian bitfield words and
are not converted.** MSCC (the original compiler) allocates bitfields
MSB-first on PowerPC; GCC on x86 allocates LSB-first. For the DK landing
script (`PlyDonkey5K_Share_ACTION_Landing`, file offset 0x4afc in `PlDk.dat`,
runtime word `0xdc000404`) the console sees `opcode = W >> 26 = 55`; the host
reads `opcode = W & 0x3f = 28` and dispatches `ftAction_80071A9C`
(set_hurt_state) with bogus fields (`bone_idx=3, state=0x1010`).

A precise walker is possible and the tables already exist:

- opcode = `(be32(word) >> 26)`; opcodes 0..9 are the general `lbCommand`
  handlers (advance 1), 10..58 are the ft actions.
- `src/melee/ft/ftaction.c:ftAction_803C0870[]` is the per-opcode advance
  count (words); `ftAction_803C06E8[]` is the opcode→function table.
- Walk each script from every `Fighter_WaitAnimData.xC` pointer (the
  `ftData->xC`/`x14` arrays), stop on opcode 0, on an out-of-range opcode, or
  on an already-converted word. For each command, repack the word(s) from
  MSB-first field order to LSB-first (per the union structs in
  `src/melee/lb/types.h`), not a plain byte swap: a byte swap maps
  `opcode` to bits 24..29, not 0..5. Pointer words (Goto/Subroutine) are
  relocation targets already in host order — skip them.
- Verify by re-running the boot and checking that the first DK landing command
  is opcode 55 (`ftAction_80072E4C`, 3 words), then 2 (timer), then 0.

The Python scratch walker that proved the opcode layout (delete/keep in
`logs/` per AGENTS.md; not run in the runtime path):

```python
p = 0x4afc  # DK landing script in the extracted PlDk.dat
while True:
    w = int.from_bytes(data[p:p+4], 'big'); op = w >> 26
    if op == 0: break
    p += 4 if op < 10 else 4 * ftAction_803C0870[op-10]
```

**Try this first — `scalar_storage_order`:** GCC's
`__attribute__((scalar_storage_order("big-endian")))` makes bitfield loads
read MSB-first from the raw bytes. A 2-line test with the raw DK word
(`dc 00 04 04`) prints `opcode=55 bone=0 state=0x404`, i.e. the console
values, with **no data conversion**. Annotating the `CmdUnion` member structs
(`src/melee/lb/types.h`, plus the item equivalents) under `PORT_PC` may fix
every script at once. Caveats: do not annotate pointer-only members
(`Command_05/07.ptr` are host pointers set by `Locate`), expect
`-Wscalar-storage-order` warnings at mixed-union accesses, and add
`-Wno-scalar-storage-order` to the port build if needed. This is a large but
mechanical ADR-0011 header patch (list it in `decomp_port.md`).

## What I tried that did not work

- **Plain byte-swap of the script pool.** Byte-swapping all words between
  sorted script pointers corrupts unrelated data: the pointers tile the whole
  data section, and the intervals bridge the WaitAnimData arrays, attrs and
  hurtbox tables. Even after skipping array ranges and capping interval length
  it double-swapped u16 fields (`ftData_x44_t`). Reverted.
- **Idempotence via the `num` bitmap alone** does not help when the wrong
  transform (byte swap) is applied first; it only prevents repeated conversion.
  Keep the bitmap (it is correct and cheap) but the script transform must be
  the field repack above.
- The decomp comment `/// Bits 0~5` on `opcode:6` means bit positions in the
  *source*, not the host memory layout; do not use it to infer endianness.
