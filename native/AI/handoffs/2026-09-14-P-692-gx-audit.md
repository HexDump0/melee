# Handoff: P-692..P-694 — GX HLE parity audit (renderer bug sweep)

**Date:** 2026-09-14
**Agent:** opencode (deepseek-v4.1-flash)
**Commit:** working tree (this commit)
**Tree state:** builds; `ctest --test-dir build/native` 21/21.

## What I did

- Audited the GX HLE (`native/decomp/gx/gx_hle.c`) and the GLES backend
  (`native/decomp/gx/gx_gl.c`) for the bug class behind P-690/P-691: state
  that is captured but consumed wrongly, or SDK semantics transcribed with a
  reference mismatch.  Method: every `GxHleDrawState` field checked for a
  consumer; every `(void)` stub in the HLE cross-referenced with its call
  sites in `decomp/src`, then the live behaviour compared against
  `aurora-reference` (Dolphin's GX) — the same oracle the P-671..P-691 work
  used.
- Fixed three silent gaps, each with a regression that fails before the fix:
  - **P-692** `decode_color`: 5/6-bit channels expand by bit replication
    (`(v << 3) | (v >> 2)` etc.), RGBA6 likewise, and `GX_RGBX8` ignores its
    X byte (alpha 255).  The HLE and the prototype decoder
    (`native/hsd/model.c`) both had the old `v * 255 / 31` rounding.
  - **P-693** `texgen_coord`: a texture-coordinate source is `(u, v, 1)`
    (Aurora `vec4f(uv, 1.0, 1.0)`), not `(u, v, 0)`; MTX3x4 q rows with a z
    coefficient or translation divided by the wrong q.
  - **P-694** TEV raster channel: `COLOR1/ALPHA1/COLOR1A1` (1/3/5) select
    rast1, `ZERO/NULL` (6/255) select black (Aurora `color_channel` /
    `color_arg_reg`).  The shader only mapped 1/5 to rast1.
- Verified the retail title frame is byte-identical to the P-691 capture
  (RMSE 0): none of the three paths is exercised by the title's draw set.

## Exact next action

Continue the audit where it stopped: the remaining "captured but unused"
fields and stubs are listed under Open questions below; the cheapest next
check is `GXSetZCompLoc` (8 call sites, captured but ignored — should be a
no-op, confirm against `GXSetPixelFmt`/Aurora) and a live-texture-object
count for the `GX_HLE_MAX_TEXOBJS` LRU (eviction falls back to
`gx.pending_tex`, which would bind the wrong texture).

## What I tried that did not work

- The sRGB/display-gamma hypothesis for the title "black bands" (Dolphin is
  ~3-4x brighter in mid-tones): a proper `x^(1/2.2)` present pass moved the
  frame mean toward Dolphin but the actual defect was P-691 (the missing
  screen-erase colour), and the pass was reverted before committing.  The
  apparent match came from ffmpeg's `eq=gamma` filter, which lifts blacks
  (`(0,1,0) -> (68,68,68)`) rather than applying a pointwise curve.  Do not
  revive a gamma pass without a pointwise A/B against Dolphin.
- `GXLoadPosMtxIndx`/`GXLoadTexMtxIndx`/`GXSetCoPlanar`/
  `GXLoadLightObjIndx`/`GXSetLightObjMtx` are stubs but have zero call sites
  in `decomp/src`, so they are not bugs.
- `GXSetTevColorS10` divides by 255; that is correct
  (`regs.cpp:bp_tev_reg` decodes `sext11 / 255`, i.e. 255 = 1.0), so the
  negative/large S10 values in `tev.c`/`sobjlib.c` are fine.
- `GXInvalidateTexAll` is a no-op but every call site is covered: the
  `GXCopyTex` callers already invalidate the CPU cache by destination
  pointer (`gx_gl_invalidate_texture`), and scene transitions clear the
  texture cache.

## Open questions

- `GX_HLE_MAX_TEXOBJS` is 128 and `GXLoadTexObj` falls back to
  `gx.pending_tex` on a slot miss.  HSD re-initialises a TObj before each
  use, so the LRU should always hold it, but a scene with >128 live TObjs
  and any use without re-init would silently bind the previous texture.
  Instrument `GXInitTexObj` to count live objects per scene — needs no
  human, just a triage counter.
- `GXSetZCompLoc` (8 sites) is captured but never read; `GXSetPixelFmt`
  (2 sites) and `GXSetDither` (2 sites) are ignored.  All three can only
  change rejection order/precision, not observable pixels, but `decomp_efb`
  cannot prove that — a human judgement call if a visual case appears.
- `GXSetFogRangeAdj` is still unreachable until the converter walks
  `HSD_FogDesc.fogadjdesc` (P-658/P-662 family).
