## What made 991 TUs compile

Two lines, both committed in `f8dc0cc14`.

1. `Runtime/platform.h` typedefs `ssize_t` as `signed int`; Emscripten's musl
   sysroot defines it as `long`. On glibc/i386 the two are the same type so C
   permits the redefinition; on wasm32 they differ and **every** TU failed.
   Guarded on `PORT_WASM`.
2. The decompilation includes `<printf.h>`, which is MSL's. `src/MSL` is
   excluded from the build, so on glibc that has been silently resolving to
   `/usr/include/printf.h`, which musl does not have. `native/decomp/shim/printf.h`
   supplies the standard declarations. Note this shim now shadows glibc's for
   the native build too — verified harmless, ctest 33/33.

**`PORT_WASM` is layered on top of `PORT_PC`, not a sibling.** 60 patch files
are gated on `PORT_PC`; a sibling macro would mean editing all of them forever.

Reproduce the census with `/tmp`-independent flags: the four native include
dirs, `-w -fgnu89-inline -ffunction-sections -fdata-sections -fno-strict-aliasing
-DLINT -DPORT_PC=1 -DPORT_WASM=1`, the shim force-include, and the native
build's three `REMOVE_ITEM` exclusions. Drop `-m32`, `-malign-double`, the SSE
flags and `-fexec-charset=CP932`.

## The port's platform layer: 47/47, and SDL3 works

Swept `native/**/*.c` (54 TUs) with `--use-port=sdl3`. The raw result was 14
failures; the real number is **zero**, and the difference is instructive
because two of the three groups were artifacts of my own census rather than
wasm problems:

- **7 files** (`gx/render.c`, `gx/shader.c`, `gx/overlay.c`, `main.c`,
  `platform/screenshot.c`, `extras/*`) include SDL**2** headers. They belong
  to `melee_prototype`, the legacy 64-bit prototype target, not the product.
  Out of scope.
- **5 files** (the viewer TUs and `sdl_audio.c`) failed a `sizeof(bool) == 1`
  assertion because I did not pass `MELEE_SHIM_REAL_STDBOOL`, which the native
  build already sets on exactly those files. They compile with it.
- **2 real failures**: `audio/sfx_debug.c` and `decomp/boot/boot_triage.c`
  include `<execinfo.h>`, glibc's backtrace API, which musl and wasm lack.
  `native/decomp/shim/execinfo.h` now supplies no-op stubs.

**SDL3's Emscripten port builds and its headers satisfy the port unchanged.**
That was an open question in ADR-0025 (pin the port vs. vendor SDL3) and the
port answer works.

**A trap worth knowing about both shims.** The shim directory is searched
*before* the system one, so a header placed there is what *every* build finds,
native included. The first version of `execinfo.h` would have silently turned
the port's symbolised crash triage into a no-op on the desktop. Both shims now
`#include_next` the real header unless `PORT_WASM` is defined. Verified: native
builds clean, ctest 33/33, and `boot_triage` still emits real backtraces.

Three flags did the work beyond the two shims:

- `-DPORT_WASM=1`, layered on `PORT_PC`.
- `-Wno-error=incompatible-function-pointer-types`. Clang errors where GCC

  complete.

Running it under node gets further than expected: the port's own banner prints
-- our `main()` executes -- and it then dies inside SDL3's video init on
`window is not defined`. That is node having no DOM, not a port problem, and
it means **MEM1 is not even the first thing to fix**; the next real test needs
a browser page. Worth knowing before anyone spends a day on address rebasing.

### New finding: wasm-ld type-checks across translation units

The link reports three function signature mismatches that GCC accepts in
silence:

    ftLib_800876B4        (i32) -> i32   vs   (i32) -> void
    gm_801677E8
    mnCharSel_802640A0

A caller that expects a return value from a function declared `void` reads
whatever is left in the return register. That is a real latent defect class in
the decompilation, and **no other toolchain we use will ever report it** --
wasm is acting as a free static analyser here. Worth a task of its own
independent of the browser port.

## Gate zero: the obvious fix is disproven

`CMD_BE` is `scalar_storage_order("big-endian")`. Clang ignores it, so emcc
decodes a real "play sound" command word as **opcode 4 instead of 17** — a
different instruction, silently. `test_bit_order` (ctest `bit_order`) pins
this; it passes under GCC and fails under emcc with six wrong decodes.

**Do not try to fix this by re-declaring the structs.** I nearly did. The
attribute does *two* things: MSB-first bit-field allocation **and** big-endian
byte order for the storage unit. Padding the group to its unit and reversing
the field order addresses only the first. Measured:

```
attribute (correct): opcode=17
pad+reverse        : opcode=0
```

The reason is structural, not a bug in the transformation: `behavior:8` sits at
console bits 25..18, which spans two bytes. After a byte swap those bits are
**not contiguous**, so no bit-field declaration in any order can express the
field. This applies to every group wider than one byte.

That leaves two real options, and choosing between them is an architecture
decision, not a mechanical edit:

- **Accessors at use sites** — portable everywhere, but churn through
  read-only `src/`, which ADR-0011 exists to prevent.
- **Byte-swap the command stream at load**, like every other archive
  structure, after which the structs become plain LSB-first bit-fields in
  padded+reversed order and need no attribute at all. This fits the port's
  architecture but collides head-on with **G-178**, which established that
  subaction command streams must stay raw because the converter did not know
  their layout. Whether that still holds now is the question to answer first.

**Option (b) is viable, and this is the measurement that says so:**
`NEXT_CMD` is `++(cmd)->u` and `sizeof(CmdUnion) == 4`, so a subaction script
is a *uniform array of 32-bit words* -- multi-word commands are just several
consecutive `NEXT_CMD`s. Byte-swapping every word of the stream at load is
therefore lossless. With the data in host order, padding each group to its
storage unit and reversing the field order **is** correct (the earlier
disproof only applies while the bytes stay big-endian). That yields plain
portable bit-fields, no attribute, and no use-site churn.

What remains to check before committing to it: whether G-178's "command
streams stay raw" still binds, and how the converter is to find each script's
extent. Note this work lands in `hsd_convert.c`, so coordinate -- another
agent has been active there.

Useful shapes for whoever takes it: of 76 `CMD_BE` structs, 63 fill their
storage unit exactly, 8 do not (`unk1`, `unk4`, `unk6`, `unk14`, `unk21`,
`set_throw_hitbox_1`, `set_throw_hitbox_2`, `spawn_hitbox_5`), and 5 have no
bit-fields at all — those five are pure byte-order cases with no bit-field
component. All 13 structs that mix base types mix only `s32` with `u32`, so
storage-unit width is never ambiguous.
